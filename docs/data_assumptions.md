# 합성 고객·거래 데이터 설계서 (v0.3 초안)

> **상태: 검토 중 (Draft)**
> 이 문서는 합성 데이터 생성기를 구현하기 **전에** 가정을 확정하기 위한 설계서입니다.
> 표에 적힌 수치는 모두 **초안 가정값**이며, 아직 공개 통계로 보정되지 않았습니다.
> 각 값은 `4. 공개 통계 보정 계획`에 따라 출처를 확인한 뒤 교체합니다.

## 1. 목적과 범위

### 1.1 왜 합성 데이터인가
- 카드사 실제 고객·승인 데이터는 개인(신용)정보라서 외부에서 사용할 수 없습니다.
- 그래서 **공개 통계의 분포를 따르는 가상의 고객과 거래 내역**을 코드로 생성합니다.
- 목표는 "현실의 완벽한 재현"이 아닙니다. **카드 상품 손익 시뮬레이션과 혜택 누수 진단에 필요한 수준의 현실성**을 확보하는 것이 목표입니다.

### 1.2 이 데이터가 쓰이는 곳
| 사용처 | 데이터에 필요한 것 |
|---|---|
| 상품 손익 시뮬레이터 (회사용) | 업종별 사용액, 월 사용액 분포(전월실적 충족 여부), 할부 비중, 해외 결제 비중 |
| 혜택 누수 진단기 (고객용) | 고객 1명의 월별·업종별 거래 내역 |
| 검증 리포트 | 생성 결과와 공개 통계를 비교할 수 있는 집계값 |

### 1.3 범위에서 제외하는 것 (v1)
- 실명, 주민번호, 카드번호, 주소, 전화번호 같은 **식별정보는 아예 생성하지 않습니다.** 고객은 `CUST_000001` 형식의 ID로만 구분합니다.
- 카드론, 리볼빙, 현금서비스, 연체 (v2 이후 검토)
- 법인카드, 가족카드, 선불카드
  - 대학생이 부모 명의 신용카드(가족카드)로 결제한 금액은 **부모 고객의 소비로 간주**하고, 대학생 고객에게는 생성하지 않습니다.

### 1.4 핵심 설계 결정: "카드 한 장의 소비"가 아니라 "고객의 전체 카드 소비"를 생성
- 생성기는 고객이 **어떤 카드를 쓰는지와 무관하게** 한 달 동안 카드로 결제하는 전체 소비를 만듭니다.
- 어떤 소비가 어떤 카드 상품으로 결제되는지는 **시뮬레이터가** 결정합니다.
- 이렇게 나누면 같은 고객 데이터로 여러 카드 상품을 공정하게 비교할 수 있습니다.
- 단, **신용카드와 체크카드는 구분**합니다. 할부 가능 여부와 전월실적 집계 방식이 다르고, 대학생처럼 체크카드 위주로 쓰는 고객층이 있기 때문입니다. (2.4 참고)

> - 비중과 월 사용액 중위값은 `4. 보정 계획`에서 공개 통계로 교체해야 합니다.

### 2.3 개인 차이(분산) 가정
- 같은 세그먼트 안에서도 월 사용액은 **로그정규분포**로 흩어진다고 가정합니다. (초안: σ = 0.6)
  - 이유: 소비액은 음수가 없고, 소수의 고액 사용자가 오른쪽 꼬리를 만들기 때문입니다.
- `online_ratio`, `installment_propensity`, `overseas_propensity`, `check_card_ratio`는 세그먼트별 평균을 중심으로 **베타분포**에서 뽑습니다. (0~1 범위 보장)

### 2.4 신용카드·체크카드 구분 (초안)
| 세그먼트 | 본인 신용카드 보유 확률 | 체크카드 사용액 비중 (보유자 기준) | 가정 근거 |
|---|---|---|---|
| S1 대학생 | 20% | 70% | 소득이 없거나 적어 신용카드 발급이 제한적. 신용카드 결제는 주로 부모 명의 가족카드(= 부모 소비로 간주) |
| S2 사회초년생 | 75% | 35% | 첫 신용카드 발급 시기. 연말정산 소득공제율 차이로 체크카드 병행 |
| S3 30대 1인가구 | 90% | 25% | |
| S4 양육가구 | 95% | 20% | 할부·혜택 목적의 신용카드 선호 |
| S5 중장년 | 95% | 15% | |
| S6 자영업 | 90% | 15% | |
| S7 고령층 | 80% | 30% | 연금 계좌 연동 체크카드 사용 |

- 신용카드 미보유 고객은 모든 거래가 체크카드입니다.
- 체크카드 거래는 **할부 불가**(`installment_months = 0`)로 생성합니다.
- 소비액 자체는 결제 수단과 무관하게 먼저 만들고, 그 뒤에 거래별로 신용·체크를 배정합니다. 결제 수단 때문에 소비 패턴이 바뀌지는 않는다고 단순화합니다.

## 3. 거래 데이터 설계

### 3.1 거래 테이블 스키마 (`transactions.csv`)
| 컬럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| `txn_id` | str | 거래 ID | `TXN_0000000001` |
| `customer_id` | str | 고객 ID | `CUST_000123` |
| `txn_datetime` | datetime | 결제 일시 | `2025-03-14 12:31:05` |
| `category` | str | 업종 (3.2 참고) | `CAFE` |
| `amount` | int | 결제 금액(원) | `5800` |
| `channel` | str | `online` / `offline` | `offline` |
| `payment_type` | str | `credit` (신용카드) / `check` (체크카드) | `check` |
| `is_overseas` | bool | 해외 결제 여부 | `false` |
| `installment_months` | int | 할부 개월 (0 = 일시불) | `3` |
| `is_cancelled` | bool | 취소 거래 여부 | `false` |
| `excluded_from_performance` | bool | 전월실적 제외 대상 업종 여부 | `false` |

> `excluded_from_performance`는 공과금, 상품권 등 **많은 카드가 전월실적에서 제외하는 거래**를 표시합니다.
> 실제 제외 기준은 상품마다 다르므로, 최종 판단은 시뮬레이터의 상품 정의(JSON)가 합니다.
> 이 컬럼은 "일반적으로 제외되는 경우가 많은 업종"이라는 참고용 플래그입니다.

- **"건당"은 결제 1회**입니다. 상품 1개 가격도, 한 달 합계도 아닙니다.
  - 카페 4번 = 거래 4건입니다. 한 달 카페 지출은 `건당 금액 × 월 결제 횟수`로 쌓입니다.
  - 온라인쇼핑 1건에는 옷(5~10만 원)뿐 아니라 생필품·식품 소액 주문(1~2만 원), 앱 결제도 섞여 있어 중위값이 옷 가격보다 낮게 잡힙니다. 옷 한 벌(6~8만 원)은 분포의 상위 30% 안쪽에 들어갑니다.
  - 대중교통 1건은 승차 1회입니다. 월 교통비는 월 승차 횟수로 현실성을 맞춥니다. (3.4.1 참고)
- 금액은 **로그정규분포**로 뽑습니다. `분산 σ`가 클수록 금액 폭이 넓습니다. 하위 10%·상위 10% 열은 실제로 생성될 금액의 범위를 보여줍니다. 평균은 중위값보다 높게 나오고, 회식이나 대량 장보기 같은 고액 거래는 꼬리 쪽에서 생성됩니다.
- 업종 중위값은 공개 통계의 **건당 평균 승인금액**으로 보정합니다. (4·5장 참고)

#### 3.2.1 세그먼트별 건당 금액 계수 (초안)
같은 업종이어도 대학생과 중장년의 건당 결제액은 다릅니다. 위 중위값에 세그먼트 계수를 곱합니다. 요금이 정해진 `TRANSIT`, `TELECOM`에는 적용하지 않습니다.

| S1 대학생 | S2 사회초년생 | S3 30대 1인 | S4 양육가구 | S5 중장년 | S6 자영업 | S7 고령층 |
|---|---|---|---|---|---|---|
| 0.8 | 1.0 | 1.1 | 1.15 | 1.15 | 1.2 | 0.9 |

- 예: 카페 중위값은 대학생 5,200원(저가 테이크아웃 비중 높음), 30대 1인가구 7,150원입니다.

- **해외 결제**는 별도 업종이 아니라 `is_overseas = true` 플래그로 표현합니다. 주로 `ONLINE_SHOP`(해외직구), `TRAVEL`, `RESTAURANT`에서 발생합니다.
- `TRANSIT`은 실제로는 월 합산 후불 청구가 많지만, v1에서는 건별 거래로 단순화합니다.
  - 대중교통 요금은 기본요금이 정해져 있어 건당 금액을 크게 올릴 수 없습니다. 1,700원은 기본요금에 거리 추가요금을 일부 반영한 값입니다. 기본요금은 보정 단계에서 현행 요금표로 확인합니다.
  - 택시는 현재 `ETC`에 포함됩니다. 별도 업종으로 분리할지는 7장에서 결정합니다.

> 🔍 **검토 포인트**: 가장 주관이 많이 들어간 표입니다. 본인의 생활 경험과 비교해 어색한 값을 먼저 고쳐 주세요.
>
> **v0.2 반영 사항**
> - S2 사회초년생: 차량 보유자가 소수라는 가정에 맞춰 `FUEL` 3% → 1%, `TRANSIT` 4% → 6%. 세그먼트 평균이라 차량 보유자 일부의 주유비만 반영됩니다.
> - S1 대학생: 여행 빈도는 낮아도 1회 지출이 커서 `TRAVEL` 3% → 8%. 대신 `ONLINE_SHOP` 18% → 16%, `CONVENIENCE`·`DELIVERY` 12% → 11%, `CULTURE_OTT` 6% → 5%로 줄였습니다.
> 보정 단계에서 "업종별 카드 승인액 비중" 공개 통계에 **전체 합계가 맞도록** 조정합니다.

### 3.4 거래 발생 방식
1. **고객별 월 사용액 결정**: `monthly_spend_median × 로그정규 노이즈 × 계절 계수`
2. **업종별 예산 배분**: 월 사용액을 3.3의 비중(+ 개인별 디리클레 노이즈)으로 업종에 나눕니다.
3. **건수 결정**: `업종 예산 ÷ 건당 금액 중위값`을 기댓값으로 하는 포아송 분포
4. **건별 금액**: 업종별 로그정규분포(중위값 × 3.2.1 세그먼트 계수)에서 뽑은 뒤 예산에 맞게 스케일 조정, 10원 단위로 반올림
5. **일시**: 요일 가중치(주말에 음식점·여행 증가)와 시간대 가중치(카페는 오전·점심, 배달은 저녁)
6. **자동납부 업종**(`TELECOM`, `UTILITY_INS`, `CULTURE_OTT` 일부): 매달 같은 날짜, 비슷한 금액으로 발생

## 6. 한계 (README에도 명시할 내용)

- 업종 비중과 금액 분포는 **공개 통계의 평균적 모습**만 반영합니다. 실제 고객 개개인의 복잡한 행동(충성 가맹점, 카드 돌려쓰기 등)은 재현하지 않습니다.
- 고객 간 상관관계(가족, 지역)와 경기 변동은 반영하지 않습니다.
- 따라서 시뮬레이터 결과는 **상품 구조를 비교하는 상대 지표**로 해석해야 합니다. 실제 수익 예측으로 쓸 수 없습니다.
